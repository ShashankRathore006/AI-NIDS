Inside the Detection Engine

The Complete Eight-Stage Pipeline

STAGE-BY-STAGE SPECIFICATION

Execution Lifecycle

Detailed technical analysis of the algorithmic operations performed at each of the eight pipeline stages.

STAGE 01

Packet Capture (Scapy)

Packet sniffing executes at Layer 2/3 utilizing Scapy’s promiscuous socket interface within a dedicated background thread. To avoid memory bloat and disk serialization delays, the capture executes with store=False. Raw Ethernet frames, Wi-Fi frames (802.11), and IP headers are dissected directly in memory.

The listener ignores link-layer noise and immediately extracts the IP protocol number (TCP=6, UDP=17), socket addresses, transport ports, frame byte lengths, and TCP control flag bitfields (SYN, ACK, RST, FIN).

STAGE 02

Flow Aggregation

Single packets cannot provide sufficient statistical distribution information to detect complex network attacks. The engine aggregates frames into bidirectional conversational flows keyed on the standard 5-tuple: (source_ip, destination_ip, source_port, destination_port, protocol).

When a packet arrives, the tracker checks an in-memory dictionary for both the forward key and the inverted reverse key (dst_ip, src_ip, dst_port, src_port, protocol). Forward and backward packet counts, byte accumulations, and timestamp histories are tracked concurrently until a 5.0-second inactivity timeout triggers flow expiration.

STAGE 03

Feature Extraction

Upon flow termination, the engine executes flow.to_features(), calculating 14 mathematical indicators that align with the CICIDS2017 schema. Crucially, the flow duration is measured with microsecond precision to match dataset training standards.

Zero payload content is stored or inspected. The system calculates volumetric transfer rates (bytes/second, packets/second), mean directional packet sizes, and TCP control flag counts.

STAGE 04

Behavioral Analysis

Reconnaissance port scans present an inherent limitation for flow-based machine learning: each probe is typically a single-packet connection to a unique destination port that expires with zero backward response, resembling a brief benign lookup.

AI-NIDS resolves this through an in-memory stateful sliding window. The tracker maintains timestamped records of probed destination ports per source IP over a 10-second window. When a single IP addresses 8 or more unique destination ports within that window, an alert is raised immediately under the BEHAVIOR detection engine tag.

STAGE 05

Machine Learning Inference

Flows that pass behavioral checks are structured into a 14-column pandas DataFrame matching the exact feature order of the trained model. The feature array is passed to a scikit-learn Random Forest ensemble consisting of 100 decision trees.

The model outputs both the predicted class (BENIGN, DoS, DDoS, Port Scan, Brute Force) and class probability distributions via predict_proba(), allowing the SOC console to filter alerts by calibrated confidence thresholds. Inference executes in under 10 milliseconds on standard CPU cores.

STAGE 06

Data Storage (SQLite)

All classified flows and detected threats are recorded into an embedded SQLite database (database/nids.db). A 12-column table captures ISO-8601 timestamps, source/destination IP addresses, source/destination ports, transport protocol, packet count, byte size, categorical prediction, confidence percentage, and detection engine type (ML or BEHAVIOR).

Using SQLite provides zero-configuration persistence without requiring a standalone daemon process like PostgreSQL or MongoDB, making AI-NIDS completely portable for edge appliance deployment.

STAGE 07

API Communication (FastAPI)

The backend service runs as an asynchronous ASGI application hosted via Uvicorn on port 8000. It provides non-blocking REST endpoints: /api/stats returns overall system flow totals and category breakdowns; /api/alerts returns the 50 most recent flow logs with optional pagination; and /api/alerts/recent-attacks streams verified threat vectors.

Native CORS middleware allows cross-origin requests from any frontend dashboard or third-party Security Information and Event Management (SIEM) pipeline.

STAGE 08

Dashboard Visualization

The Live SOC Dashboard (hosted on port 3000) provides a real-time defense console. It continuously evaluates live telemetry from the FastAPI service to calculate a dynamic DEFCON Threat Posture score (DEFCON 5 Nominal through DEFCON 1 Severe Intrusion).

Real-time Chart.js streams visualize flow velocity and threat timelines, multi-criteria filters enable rapid log inspection, and the Web Audio API synthesizes audible frequency alerts on critical detections.

DETECTION ARCHITECTURE

Dual Detection Engines: Behavioral vs. Machine Learning

AI-NIDS employs a hybrid detection strategy. Rather than forcing a machine learning model to detect attacks it is architecturally unsuited for, the system couples stateful heuristics with statistical machine learning.

ENGINE A // BEHAVIORAL DETECTION

Stateful Sliding-Window Tracker

Targets reconnaissance scanning sweeps where an adversary rapidly probes multiple network ports to discover running services.

  • Detection Mechanism: In-memory sliding time window maintaining a set of probed destination ports per source IP.
  • Time Window: 10 seconds continuous rolling duration.
  • Threshold: ≥8 unique destination ports triggers an immediate alert.
  • Why Heuristic: Single-probe flows do not contain enough statistical anomalies for ML; tracking state across flows is deterministic and produces zero false negatives on fast sweeps.
  • Latency: Zero flow-delay. Triggers immediately on the 8th unique port packet.
ENGINE B // MACHINE LEARNING DETECTION

Random Forest Flow Classifier

Classifies multi-packet network flows based on mathematical distributions across 14 extracted statistical indicators.

  • Model Architecture: Random Forest with 100 decision trees trained with scikit-learn.
  • Target Classes: BENIGN, DoS, DDoS, Port Scan, Brute Force.
  • Input Dimensionality: 14 numerical features (durations, rates, sizes, TCP flags).
  • Why Random Forest: Exceptional resistance to overfitting, deterministic execution, and fast CPU inference (<10ms) without GPU requirements.
  • Output: Multi-class probability distribution and primary categorical prediction.
FEATURE ENGINEERING

The 14-Feature Input Vector

Extracted directly from bidirectional flow state upon session expiration. The column order strictly mirrors the trained Random Forest model schema.

# Feature Name Data Type Measurement Unit Mathematical Definition & Detection Purpose
01 Destination Port Integer Port (0–65535) Target socket port. Identifies well-known services (e.g. 21 FTP, 22 SSH, 80 HTTP) and indicates targeted exploit focus.
02 Flow Duration Float Microseconds (μs) Total elapsed duration from first packet to last packet. Matches the CICIDS2017 microsecond representation.
03 Total Fwd Packets Integer Count Total packets transmitted from initiator to receiver within the conversation session.
04 Total Backward Packets Integer Count Total response packets transmitted from receiver back to initiator. High asymmetry flags DoS/DDoS floods.
05 Total Length of Fwd Packets Integer Bytes Cumulative payload and header bytes transmitted in the forward direction.
06 Total Length of Bwd Packets Integer Bytes Cumulative payload and header bytes transmitted in the backward reply direction.
07 Flow Bytes/s Float Bytes / Second Total bytes transferred divided by flow duration in seconds. Critical indicator of volumetric flooding.
08 Flow Packets/s Float Packets / Second Total packet count divided by flow duration in seconds. Spikes during high-frequency flood or brute-force retries.
09 Fwd Packet Length Mean Float Bytes Average size of forward packets. High consistency indicates automated fuzzing or script-driven exploitation.
10 Bwd Packet Length Mean Float Bytes Average size of backward response packets. Differentiates normal web traffic from rejected unauthorized attempts.
11 SYN Flag Count Integer Count Number of packets containing the TCP Synchronize flag. Spikes during SYN floods and half-open scanning.
12 ACK Flag Count Integer Count Number of packets containing the TCP Acknowledgment flag. Measures connection handshake completion.
13 RST Flag Count Integer Count Number of packets containing the TCP Reset flag. High frequency indicates connection teardowns and closed port sweeps.
14 Average Packet Size Float Bytes Cumulative flow bytes divided by total packets. Unifies overall conversational footprint into a single metric.
ENGINEERING HONESTY

Technical Limitations & Design Considerations

Rigorous cybersecurity engineering requires explicit acknowledgment of operational trade-offs and structural constraints. Below are the documented considerations for AI-NIDS.

CONSIDERATION 01

Offline Accuracy vs. Live Detection Gap

There is a well-documented divergence between offline benchmark performance (99.74% on CICIDS2017) and real-world live traffic classification. Academic datasets are extracted via offline PCAP post-processing (e.g. CICFlowMeter) where complete bi-directional flows are finalized without socket packet loss or CPU jitter.

In a live production environment, streaming flow reconstruction must handle dynamic timeouts, packet fragmentation, and missing ACK responses. Consequently, live detection confidence scores are more variable than offline benchmark metrics.

CONSIDERATION 02

Statistical Class Overlap Between Floods

Volumetric floods share fundamental statistical characteristics across attack categories. A high-velocity credential brute-force attack (e.g. rapid SSH password attempts) generates a burst of compact packets at high frequency, exhibiting volumetric rates and packet length distributions that heavily overlap with DoS and DDoS traffic.

During empirical live validation, multi-device flooding was classified under the Brute Force label due to this statistical similarity. Rather than concealing this, AI-NIDS reports it as a documented class-overlap finding.

CONSIDERATION 03

Single-Packet Reconnaissance Limitations

Pure flow-based machine learning models are structurally blind to single-packet reconnaissance probes. A stealthy SYN scan sends one packet to port 80, one to port 443, and one to port 22. Each flow terminates with 1 packet and 0 reply bytes, appearing statistically identical to dropped benign packets.

This limitation directly motivated our decision to implement Engine A (the stateful sliding-window tracker), demonstrating that production intrusion detection cannot rely on standalone machine learning models without behavioral context.
